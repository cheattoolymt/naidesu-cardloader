# 📇 naidesu-cardloader

> (何もかも)ないです — バイナリ ⇄ 紙のパンチカード変換ツール（A4 / 300dpi）

任意のファイル（バイナリ）を、A4に印刷できる「パンチカード」画像に変換し、
それを **印刷 → スキャン** して、再びバイナリに復元するための
完全ブラウザ完結（サーバ不要）の静的Webアプリです。

- **作成 (Creator)**: `バイナリ → カード画像(PDF / PNG / JPG) → 印刷`（**1KB〜8KB** の密度モード＋**誤り訂正レベル**を選択可）
- **読み取り (Decoder)**: `印刷物を300dpiでスキャン → 自動検出 → 誤り訂正 → バイナリ復元`（**モード・誤り訂正レベルとも自動判別**）

> **✨ 誤り訂正（リードソロモン）対応**: GF(256) 上の Reed-Solomon 符号を実装し、
> 印刷物の**汚れ・かすれ・JPEG劣化で一部のマスが化けても自動で訂正**できるようになりました。
> 訂正の強さ（パリティ量）は作成時に **なし / 低(≈10%) / 中(≈20%) / 高(≈30%)** の
> **4段階から選択**できます。
> 攻めた **5KB モード（1ページ 5718 byte・1セル 1.00mm 維持）** に加え、**余白を切り詰めて A4 を使い切る**設計を
> さらに推し進め、**6KB / 7KB / 8KB モード（最大 1ページ 9209 byte・実質9KB超・1セル 0.79mm）** に増量しました。
>
> **🧹 無駄をなくす（さらなる余白削減で A4 を使い切る・v5）**: v4 は端余白 7.6mm で
> データグリッドは A4 の **69.1%** でした。家庭用プリンタの実際の印刷可能領域（概ね上下左右 5mm 前後）
> にはまだ余裕があるので、端余白を **5.08mm** まで削り、四隅ファインダ・隙間も切り詰めて、
> データグリッドを **A4 の 74.2%** まで拡大しました。この“紙を使い切る”改良で、
> **マスをこれ以上小さくせずに**、同じセル物理サイズのまま容量だけを増やしています
> （5KB は同じ 1.00mm で 5376→**5718 byte**、8KB は 0.81→0.79mm のほぼ据え置きで 8176→**9209 byte**）。
> **5〜8KB のマスは縮めすぎず**（5KB は **1.00mm 以上を維持**）、**300dpi でも安定して読める**まま
> **1枚あたり最大 9209 byte（≈9KB・目標の 9〜10KB を達成）** に増やしました。
>
> **🏷️ フッタ表記をバイナリの箱の直下へ**: 人間可読のフッタ
> （`naidesu-cardloader  <モード>  ECC:<レベル>  page x/y  payload …B  total …B`）を、
> 従来のページ最下端から**バイナリの箱（データグリッド）のすぐ下**に移動し、どのカードが何かを一目で判別できます。
>
> **🗜️ 圧縮対応（限界まで自動圧縮）**: 作成時に**チェックを入れるだけ**で、ファイルを
> **限界まで圧縮**してから紙に載せます（＝同じデータをより少ない枚数に）。方式は
> **deflate-raw / gzip / brotli / 日本語辞書付き deflate** を全部試して**最小のものを自動選択**。
> 読み取り側は**圧縮されているかを自動判別して自動で展開**します（手動操作は不要）。
> **バイナリは絶対に破損させません**：可逆な範囲でしか圧縮せず、縮まないデータは
> 自動的に**無圧縮(STORE)へフォールバック**し、選んだ方式で展開して**元と完全一致するかを
> 生成時に自己検証**します（不一致なら無圧縮に切替）。

pdf.js / jsPDF / pako（辞書 deflate 用）を利用し、外部サーバへデータを送りません（オフラインでも動作）。

## 🚀 使い方

`index.html` をブラウザで開くだけです（GitHub Pages 等の静的ホスティングでも動作）。

### ① 作成（バイナリ → 紙）
1. `creator.html` を開く
2. 変換したいファイルを選択（テキスト / 画像 / zip など何でも可）
3. **密度モード**を選ぶ（すべて **A4 全面**を使うレイアウト・数値は**総容量**）
   - **1KB モード**（100×145・1ページ 1787 byte・1セル 1.79mm・マスが大きく読み取り安定・**推奨**）
   - **2KB モード**（118×170・1ページ 2478 byte・1セル 1.52mm・枚数を減らせる）
   - **3KB モード**（137×198・1ページ 3356 byte・1セル 1.31mm・高密度）
   - **4KB モード**（157×227・1ページ 4435 byte・1セル 1.14mm・4KB のファイルも 1 枚に集約）
   - **5KB モード**（178×258・1ページ 5718 byte・1セル 1.00mm・**マス1mm以上を維持**）
   - **6KB モード**（196×284・1ページ 6933 byte・1セル 0.91mm）
   - **7KB モード**（212×306・1ページ 8082 byte・1セル 0.84mm・実質8KB超）
   - **8KB モード**（226×327・1ページ 9209 byte・1セル 0.79mm・**最高密度・実質9KB超/圧縮併用で10KB超**）
4. **誤り訂正レベル**を選ぶ（**段階的に調整可**）
   - **なし**（訂正しない・総容量をフルにデータへ）
   - **低（約10%）** — わずかな汚れ・かすれを訂正
   - **中（約20%）** — 既定。実用的な訂正力（推奨）
   - **高（約30%）** — 強い汚れ・折れにも耐える（そのぶん正味容量は減る）
4.5. **🗜️ 圧縮**（チェックを入れるだけ・既定ON）
   - チェックすると、ファイルを**限界まで自動圧縮**してから紙に載せます（枚数削減）。
   - 方式（deflate/gzip/brotli/**日本語辞書付き deflate**）は**自動選択**。手動指定は不要。
   - テキスト/JSON/HTML は大きく縮みます（日本語短文で 60%超・長文でも +10〜15% 上乗せ）。
   - バイナリは可逆な範囲でのみ圧縮し、縮まなければ**無圧縮(STORE)**にフォールバック（**破損なし**）。
   - **読み取り側は自動で展開**するので、圧縮したかどうかを覚えておく必要はありません。
5. 出力形式を選ぶ
   - **PDF**（複数ページを1ファイルに・推奨）
   - **PNG / JPG**（ページごとに個別ダウンロード）
6. 「カードを生成してダウンロード」
7. **A4に等倍（100% / 実サイズ）で印刷**（四隅の黒い■を切らないこと）

> **総容量と正味容量（＝実際に入るデータ量）**: 総容量はモードで決まり、
> そこから誤り訂正のパリティを差し引いた分が正味容量です。
>
> | モード | 総容量 | 1セル | 正味 (なし) | 正味 (低≈10%) | 正味 (中≈20%) | 正味 (高≈30%) |
> |--------|-------:|------:|-----------:|-------------:|-------------:|-------------:|
> | 1KB | 1787 B | 1.79mm | 1787 B | 1603 B | 1421 B | 1239 B |
> | 2KB | 2478 B | 1.52mm | 2478 B | 2218 B | 1958 B | 1698 B |
> | 3KB | 3356 B | 1.31mm | 3356 B | 2992 B | 2639 B | 2301 B |
> | 4KB | 4435 B | 1.14mm | 4435 B | 3967 B | 3499 B | 3031 B |
> | 5KB | 5718 B | 1.00mm | 5718 B | 5120 B | 4522 B | 3924 B |
> | 6KB | 6933 B | 0.91mm | 6933 B | 6205 B | 5481 B | 4779 B |
> | 7KB | 8082 B | 0.84mm | 8082 B | 7250 B | 6418 B | 5586 B |
> | 8KB | 9209 B | 0.79mm | 9209 B | 8247 B | 7308 B | 6372 B |
>
> いずれも正味容量を超えるファイルは自動的に複数ページに分割されます。
> **圧縮（既定ON）と併用**すれば、テキスト/JSON/HTML は 8KB モード 1 枚に**実効 10KB〜数十KB 相当**が載ります。
>
> **なぜ 6〜8KB モードを増量できたのか（無駄の除去＋誤り訂正）**: 4KB モードまでは
> 「マスを縮めすぎると 1 マスの読み違いが即データ破損」になるため高密度化に慎重でしたが、
> リードソロモン誤り訂正で**多少マスが化けても自動訂正**できるようになりました。
> さらに今回(v5)は **“セルを縮める”のではなく、余白の無駄をさらに無くして紙を使い切る**ことで容量を稼ぎ、
> **マスは 300dpi で読める 0.79mm 以上に保った**まま（5KB は **1.00mm 以上を維持**）**9209 byte/枚**を実現しています
> （実 Canvas + 実 JPEG(0.9) を経ても ECC 込みで byte-exact に復元できることをテストで実証済み）。
>
> **A4 を使い切るレイアウト（v5）**: 端余白 `QUIET` を v4 の 90px(7.6mm) から **60px(5.08mm)** に、
> ファインダ(110→100px)・隙間(30→24px)も切り詰め、データグリッドを v4 の `2020×2978` から **`2112×3056`**
> （＝A4 の **69.1% → 74.2%**）へ拡大しました。この面積拡大だけで、**同じセルサイズのまま**
> 約 1.07 倍（v3 比では約 1.23 倍）のバイトが載ります。余白は家庭用プリンタの印刷可能領域
> （概ね上下左右 5mm 前後）に十分収まる安全値です。

### ② 読み取り（紙 → バイナリ）
1. 印刷したカードを **300dpi程度でスキャン**、または正面から真っ直ぐ撮影
2. `decoder.html` を開き、画像 / PDF を読み込む
3. 四隅の黒い■（ファインダ）を **自動検出** → 赤いグリッド枠が表示される
4. ズレていたら、赤枠の四隅（青いハンドル）を **ドラッグして調整**（スマホはタッチ操作可）
5. 「このページを解析して追加」→ **モード・誤り訂正レベルを自動判別**し、
   ヘッダのリードソロモン符号で**汚れ・かすれによる誤りを自動訂正**（訂正バイト数を表示）
6. ヘッダのページ番号で自動整理 → 全ページが揃ったら「全ページ結合してファイル保存」
   → 結合したデータが**圧縮コンテナなら自動判別して自動展開**（方式・展開後サイズを表示）し、
   元ファイルが復元されます（**圧縮の有無を意識する必要はありません**）

## 🧩 仕組み

### カードフォーマット（`js/card-format.js` に集約）
エンコーダ・デコーダの両方がこの1ファイルを共有し、幾何形状とヘッダ仕様のズレを防ぎます。
**密度モード**は共通のジオメトリ（用紙・余白・四隅ファインダ位置・データ領域の大きさ）を
保ったまま、その共通の長方形を `cols × rows` に細分するセル数だけを切り替えます。
ファインダ位置が全モード共通なので、自動位置検出はモードに依らず1つのロジックで動きます。

> **データ領域は A4 を“もっと”使い切る（v5・さらなる余白削減）**: 全モード共通のグリッド矩形は
> **`2112 × 3056 px`**（ページ 2480×3508px から端余白 60px＝5.08mm・四隅ファインダ・隙間・下端フッタを
> 除いた領域）で固定です。v4（`2020 × 2978`・A4 の 69.1%）から端余白を 90→60px、ファインダを
> 110→100px、隙間を 30→24px へ切り詰めて **A4 の 74.2%** まで拡大しました。**マスは縮めていません**
> ——同じセル物理サイズのまま容量だけを増やす「無駄の除去」です。

| 項目 | 1KB | 2KB | 3KB | 4KB | 5KB | 6KB | 7KB | 8KB |
|------|----:|----:|----:|----:|----:|----:|----:|----:|
| 用紙/解像度 | A4 / 300dpi（`2480 × 3508 px`）全モード共通 |||||||| 
| データ領域 | `2112 × 3056 px`（全モード共通）|||||||| 
| グリッド | `100×145` | `118×170` | `137×198` | `157×227` | `178×258` | `196×284` | `212×306` | `226×327` |
| 1セル(mm) | `1.79` | `1.52` | `1.31` | `1.14` | `1.00` | `0.91` | `0.84` | `0.79` |
| ヘッダ行 | 2 | 2 | 2 | 1 | 1 | 1 | 1 | 1 |
| 総容量(B) | `1787` | `2478` | `3356` | `4435` | `5718` | `6933` | `8082` | `9209` |

> **ヘッダ行はモードによって 1〜2 行**: RS 保護ヘッダは 18 byte(144 bit) あり、
> 行幅が狭いモード（1KB～3KB）では 1 行に収まらないため `ceil(144/cols)` 行をヘッダに充てます。
>
> **300dpi でのセル物理サイズと「マスを縮めない」方針**: **5KB モードは 1セル `1.00mm` 以上を維持**します。
> 最も高密度な 8KB モードでも 1セル ≈ `9.35px`(`0.79mm`) を確保しており、v4 と同等（8KB は 0.81→0.79mm と
> ほぼ据え置き）です。容量アップは**セルの縮小ではなく余白の無駄の除去**で稼いでおり、8KB モードは
> **1枚 9209 byte（≈9KB・目標の 9〜10KB を達成）**、圧縮併用で実質 10KB 超が 1 枚に載ります。
> フッタの人間可読テキスト（`naidesu-cardloader  8KB  ECC:MED  page 1/1 …`）は**バイナリの箱のすぐ下**に印字されます。

### 圧縮（限界まで自動圧縮 + 自動展開・`js/compress.js`）
作成時にチェックを入れると、カードに載せる前にファイルを圧縮します。**圧縮とカードの
誤り訂正(RS)は独立**していて、`圧縮 → その結果をカードのペイロードとして RS 符号化`
という二段構えです（圧縮でデータ量が減るほど、必要な枚数も減ります）。

**方式は全部試して最小を自動選択**します（破損厳禁の三重の安全策つき）:

| method | key | 内容 | 目安 |
|-------:|-----|------|------|
| 0 | STORE | 無圧縮（そのまま） | 縮まない時のフォールバック |
| 1 | deflate-raw | ヘッダ/チェックサムなしの DEFLATE（最小オーバヘッド） | 生UTF-8比 約40〜50%削減 |
| 2 | gzip | GZIP | deflate の保険 |
| 3 | brotli | Brotli（対応環境のみ） | deflate より強い ≈50%削減 |
| 4 | deflate+日本語辞書 | deflate-raw に**日本語プリセット辞書**（preset dictionary） | 日本語短文で最大60%超・長文でも +10〜15% 上乗せ |

- **日本語辞書付き deflate** は、zlib/pako の *preset dictionary* 機能で、ひらがな・カタカナ・
  頻出の助詞/語尾/記号・HTML/JSON 断片などをまとめた辞書を LZ77 の初期ウィンドウに載せます。
  **辞書は符号語に含まれず**（両側が同じ辞書を共有）、本文中の頻出トークンが「辞書内への
  後方参照」として短く符号化されるため、辞書前置き(prefix priming)と違い**オーバヘッドがゼロ**です。
- **破損厳禁の三重の安全策**:
  1. 複数方式で圧縮し、**最小の符号語**を選ぶ
  2. 圧縮してもヘッダ込みで小さくならなければ**無圧縮(STORE)**にする
  3. 選んだ方式で**その場で展開し、元と完全一致するかを自己検証**（不一致なら STORE に切替）
- **圧縮コンテナ（先頭 8byte ヘッダ + 本体）**:

  | offset | 内容 |
  |--------|------|
  | 0..2 | MAGIC `0x4E 0x5A 0x31`（"NZ1" = Naidesu Zip v1） |
  | 3 | method（0..4） |
  | 4..7 | 元バイト数（big-endian 32bit） |
  | 8.. | 本体（method に応じた符号語 / STORE なら生データ） |

  読み取り側は結合後のバイト列の先頭 3byte が MAGIC なら圧縮コンテナと判定して**自動展開**し、
  そうでなければ**旧来の無圧縮データとして素通し**します（**後方互換**：圧縮なしで作った
  既存カードもそのまま読めます）。展開後は元バイト数と長さが一致するかを検証します。
- **環境**: 圧縮/展開の deflate-raw・gzip・brotli はブラウザ標準の
  [Compression Streams API](https://developer.mozilla.org/docs/Web/API/CompressionStream)
  （Baseline 2023-05〜。brotli は対応環境のみ試行）を使用。辞書 deflate だけは辞書 API が
  標準に無いため [pako](https://github.com/nodeca/pako)（`js/vendor/pako.min.js`）を使います。
  すべてクライアントサイド処理（アップロードなし・オフライン可）。

### 誤り訂正（Reed-Solomon over GF(256)）
`js/reed-solomon.js` に GF(256)（原始多項式 `0x11d`、QR コード標準）のリードソロモン
符号化/復号化を実装しています。系統符号化 `[データ | パリティ]` で、ブロック長 `N=255`、
パリティ `nsym` バイトにつき **最大 `nsym/2` バイト/ブロックの誤りを訂正**できます
（Berlekamp-Massey で誤り位置多項式、Chien 探索で位置、Forney で値を復元）。

訂正レベルはパリティ比で段階化しています（ブロック単位で偶数に丸めて適用）:

| レベル | key | パリティ比 | 意味 |
|------|-----|---------|------|
| 0 | none | 0% | 訂正なし（総容量＝正味） |
| 1 | low | ≈10% | 軽微な汚れ・かすれ |
| 2 | med | ≈20% | 実用的（既定・推奨） |
| 3 | high | ≈30% | 強い汚れ・折れ |

本文はページごとに RS 符号化され、デコーダはヘッダから判別した訂正レベルで
自動的に復号・訂正します。訂正能力を超える損傷だけクリーンに失敗検出します。

### ヘッダ（12 byte の論理情報 + RS パリティ 6 byte = 18 byte）
ヘッダ自体もリードソロモン（`nsym=6`、最大 3 byte 訂正）で保護しており、
ヘッダ行の汚れでもページ情報（モード/ECC/ページ番号）を復元できます。論理 12 byte の内訳:

| offset | 内容 |
|--------|------|
| 0..1 | MAGIC `0x4E 0x43`（"NC" = Naidesu Card） |
| 2 | VERSION+モードID+ECC（下位3bit=VERSION(=3)、次3bit=モードID `0:1KB〜7:8KB`、上位2bit=ECCレベル `0〜3`） |
| 3 | pageIndex（0始まり） |
| 4 | totalPages（総ページ数） |
| 5..6 | このページの有効ペイロード長（big-endian 16bit） |
| 7..10 | ファイル全体のバイト数（big-endian 32bit） |
| 11 | チェックサム（0..10 の XOR） |

このヘッダにより、**バラバラの順序でページを読み込んでも正しく結合**でき、
ズレた読み取りは**チェックサムNGで検出**して赤枠の再調整を促します。

**モード・ECCレベルの自動判別**: デコーダはカードのモードも ECC レベルも事前に知りません。そこで
1KB〜8KB すべてのグリッドでヘッダ行を試し読み（RS でヘッダを復号）し、`MAGIC` + `checksum` が通り、
さらに**ヘッダ内モードIDとサンプリングに使ったグリッドが一致**したものを採用し、ヘッダ内の ECC レベルで
本文を復号・訂正します。これにより、読み取り側でモードも訂正レベルも手動選択する必要はありません（古い VERSION 2 ヘッダも後方互換で読めます）。

### 自動位置検出
四隅に **黒い正方形のファインダマーカー**を配置しています。左上(TL)だけは
「黒四角の中に白抜き＋中心に黒点」の特別マークにして**向きを一意**にしています。

デコーダは以下の流れで四隅を自動検出します（歪みなし・まっすぐ動かす前提）:

1. グレースケール化 → **大津の二値化**（縮退対策として黒/白平均の中点を採用）
2. **連結成分ラベリング**で黒い塊を抽出
3. サイズ・アスペクト比・充填率で「ファインダらしい塊」を選別
4. 画像の四隅に最も近い塊の重心を採用
5. ファインダ中心 → データグリッド四隅へ幾何補正（`finderToGrid`）

検出できない/ズレる場合は、赤枠の四隅を手で合わせれば確実に読めます。

## 🧪 テスト

Node.js（Canvas不要の純JS）で往復一致を検証します。

```bash
npm test                       # roundtrip + autodetect + compress をまとめて実行
# 個別に実行する場合:
node test/roundtrip.test.js    # 生成→理想座標サンプリング→復元 が byte-exact
node test/autodetect.test.js   # 生成→自動検出(otsu+連結成分)→復元 が byte-exact
node test/compress.test.js     # 圧縮往復 + 圧縮ON/OFFのカード全往復 が byte-exact
```

`compress.test.js` は、空/1byte/日本語/JSON/HTML/英語/ランダムバイナリ/ゼロ埋め等を対象に、
**圧縮コンテナ単体の往復**、**圧縮を挟んだカード全往復（各モード×ECC）**、および
**ランダムバイナリが STORE にフォールバックしてヘッダ(8B)以外増えない**ことを検証します。
実ブラウザCanvasを通した圧縮E2Eは `test/compress-e2e-browser.html`（タイトルが "E2E PASS" で成功）。

実Canvas + 実JPEG(0.9)圧縮を経た自動検出E2E（特に **5KBモードの高密度セル(0.93mm)が
JPEG圧縮後も RS 誤り訂正込みで読めること**の確認）は Node でも実行できます（`canvas` が必要）。
メモリ節約のため `--expose-gc` 付きで代表 3 ケースに絞っています。

```bash
npm install                    # devDependency の canvas を導入
npm run test:jpeg              # node test/jpeg-e2e.node.js
```

ブラウザでの実描画・実JPEG圧縮を含むE2Eは、静的サーバを立てて開きます。

```bash
python3 -m http.server 8000
# → http://localhost:8000/test/browser-e2e.html （タイトルが "E2E PASS" になれば成功）
```

検証済みケース（**1KB 〜 8KB の全8モード × ECC レベル 0〜3**）:
小さいテキスト / 正味容量ぴったり / 複数ページ / スキャン解像度違い(1.3x) / 余白(平行移動)付き /
**汚れ・かすれシミュレート（セルのランダム反転を RS が訂正）** / **JPEG圧縮(0.9)経由**（特に **5KBモード(1セル 0.93mm)が JPEG圧縮後も読めること**） /
**モード・ECCレベル自動判別**。いずれも byte-exact で復元。

リードソロモンコアの単体検証は `node test/roundtrip.test.js` 内の ECC 往復マトリクスとシミュレートで実施されます。

## 💡 印刷・スキャンのコツ

- 印刷は **等倍（100% / 実サイズ / 拡大縮小なし）** が理想。
- 白黒でOK。**四隅の黒い■を切らない**（自動位置合わせに必須）。
- スキャンは **300dpi 前後**。傾き・歪みは無い前提なので、原稿はまっすぐ置く。
- 撮影する場合は真上から、影・反射が入らないように。
- うまく読めないときは Decoder の赤枠を手動で微調整、または「白黒反転」を試す。

## ⚙️ 技術

- Pure HTML / CSS / JavaScript（フレームワーク不使用）
- [pdf.js](https://mozilla.github.io/pdf.js/) — PDFの読み込み・描画
- [jsPDF](https://github.com/parallax/jsPDF) — カードのPDF出力
- 自前実装の **Reed-Solomon over GF(256)**（レベル選択可能な誤り訂正）
- **圧縮**: ブラウザ標準の [Compression Streams API](https://developer.mozilla.org/docs/Web/API/CompressionStream)
  （deflate-raw / gzip / brotli）＋ [pako](https://github.com/nodeca/pako)（辞書付き deflate）。
  多方式から最小を自動選択し、自動展開・破損検知つき
- すべてクライアントサイド処理（アップロードなし・オフライン可）
