# 📇 naidesu-cardloader

> (何もかも)ないです — バイナリ ⇄ 紙のパンチカード変換ツール（A4 / 300dpi）

任意のファイル（バイナリ）を、A4に印刷できる「パンチカード」画像に変換し、
それを **印刷 → スキャン（または撮影）** して、再びバイナリに復元するための
完全ブラウザ完結（サーバ不要）の静的Webアプリです。

- **作成 (Creator)**: `バイナリ → カード画像(PDF / PNG / JPG) → 印刷`（**1KB / 2KB / 3KB** の密度モードを選択可）
- **読み取り (Decoder)**: `印刷物を300dpiでスキャン → 自動検出 → バイナリ復元`（**モードは自動判別**）

pdf.js / jsPDF を利用し、外部サーバへデータを送りません（オフラインでも動作）。

---

## 🚀 使い方

`index.html` をブラウザで開くだけです（GitHub Pages 等の静的ホスティングでも動作）。

### ① 作成（バイナリ → 紙）
1. `creator.html` を開く
2. 変換したいファイルを選択（テキスト / 画像 / zip など何でも可）
3. **密度モード**を選ぶ（すべて **A4 全面**を使うレイアウト）
   - **1KB モード**（96×143・1ページ 1704 byte・マスが大きく読み取り安定・**推奨**）
   - **2KB モード**（112×167・1ページ 2324 byte・枚数を減らせる）
   - **3KB モード**（130×194・1ページ 3136 byte・高密度）
   - **4KB モード**（149×222・1ページ 4116 byte・**4KB のファイルも 1 枚に集約**できる最高密度）
4. 出力形式を選ぶ
   - **PDF**（複数ページを1ファイルに・推奨）
   - **PNG / JPG**（ページごとに個別ダウンロード）
5. 「カードを生成してダウンロード」
6. **A4に等倍（100% / 実サイズ）で印刷**（四隅の黒い■を切らないこと）

> 1ページの容量はモードで決まります。
> - **1KB モード**: **1704 byte/枚** — 1KB(1024byte)を余裕で1枚に。
> - **2KB モード**: **2324 byte/枚** — 2KB(2048byte)を余裕で1枚に。
> - **3KB モード**: **3136 byte/枚** — 3KB(3072byte)を余裕で1枚に。
> - **4KB モード**: **4116 byte/枚** — 4KB(4096byte)を**余裕で1枚に**。
>
> いずれも容量を超えるファイルは自動的に複数ページに分割されます。
>
> **A4 全面を使うレイアウトにしました（4KB を1枚に）**:
> 以前はデータグリッドが「正方形」(`1860×1860`)で、A4(2480×3508px)の
> **上半分強しか使っていません**でした。データ領域を **A4 全高**(`1860×2778`)に拡張した
> ことで、`149×222` で 4116 byte を確保でき、1セルは **`1.06mm`** — 旧 3KB モード(0.98mm)より
> むしろ大きくなります。セルを縮めずに 4KB を1 枚へ収められるのは、この全面活用のおかげです。

### ② 読み取り（紙 → バイナリ）
1. 印刷したカードを **300dpi程度でスキャン**、または正面から真っ直ぐ撮影
2. `decoder.html` を開き、画像 / PDF を読み込む
3. 四隅の黒い■（ファインダ）を **自動検出** → 赤いグリッド枠が表示される
4. ズレていたら、赤枠の四隅（青いハンドル）を **ドラッグして調整**（スマホはタッチ操作可）
5. 「このページを解析して追加」→ ヘッダのページ番号で自動的に整理される
6. 全ページが揃ったら「全ページ結合してファイル保存」→ 元ファイルが復元されます

## 🧩 仕組み

### カードフォーマット（`js/card-format.js` に集約）
エンコーダ・デコーダの両方がこの1ファイルを共有し、幾何形状とヘッダ仕様のズレを防ぎます。
**密度モード**は共通のジオメトリ（用紙・余白・四隅ファインダ位置・データ領域の大きさ）を
保ったまま、その共通の長方形を `cols × rows` に細分するセル数だけを切り替えます。
ファインダ位置が全モード共通なので、自動位置検出はモードに依らず1つのロジックで動きます。

> **データ領域は A4 全面**: 全モード共通のグリッド矩形は `1860 × 2778 px`
> （ページ全高 3508px から上下余白と下端フッタ分を除いた領域）で固定です。
> 以前の正方形グリッド（`1860 × 1860`）は A4 の上半分強しか使っていませんでした。

| 項目 | 1KB モード | 2KB モード | 3KB モード | 4KB モード |
|------|-----------|-----------|-----------|-----------|
| 用紙 | A4 固定 | A4 固定 | A4 固定 | A4 固定 |
| 解像度 | 300 dpi（`2480 × 3508 px`） | 同左 | 同左 | 同左 |
| データ領域 | `1860 × 2778 px`（全モード共通） | 同左 | 同左 | 同左 |
| グリッド | `96 × 143` | `112 × 167` | `130 × 194` | `149 × 222` |
| 1セル | 約 `19.4px` ≈ `1.64mm` | 約 `16.6px` ≈ `1.41mm` | 約 `14.3px` ≈ `1.21mm` | 約 `12.5px` ≈ `1.06mm` |
| ヘッダ | 先頭1行（96bit → 先頭12byte使用） | 先頭1行 | 先頭1行 | 先頭1行 |
| ペイロード | `95 × 96 = 1704 byte` | `112 × 166 = 2324 byte` | `130 × 193 = 3136 byte` | `149 × 221 = 4116 byte` |

> **300dpi でのセル物理サイズ**: 最も高密度な 4KB モードでも 1セル ≈ `12.5px`(`1.06mm`) を
> 確保しており、300dpi スキャンで安定して読めるサイズを維持しています。
>
> **なぜ 4KB を 1 枚にできるようになったのか**: 以前はデータ領域を正方形（`1860×1860`）に
> 限定していたため、4096 byte を 1 枚に入れるには `192×192`、すなわち 1セル ≈ `0.82mm` まで
> 縮小が必要でした。ところがデータ領域を **A4 全高**（`1860×2778`）に拡張すると、
> `149×222` で 4116 byte を確保でき、1セルは `1.06mm` — 旧 3KB モード(0.98mm)よりむしろ
> 大きくなります。これによりセルを縮めずに 4KB を1枚へ収められるようになりました。
> 4116 byte を超えるファイルは 4KB モードで自動的に複数ページへ分割されます。

### ヘッダ（12 byte）
| offset | 内容 |
|--------|------|
| 0..1 | MAGIC `0x4E 0x43`（"NC" = Naidesu Card） |
| 2 | VERSION+モードID（下位4bit=VERSION(=2)、上位4bit=モードID `0:1KB / 1:2KB / 2:3KB / 3:4KB`） |
| 3 | pageIndex（0始まり） |
| 4 | totalPages（総ページ数） |
| 5..6 | このページの有効ペイロード長（big-endian 16bit） |
| 7..10 | ファイル全体のバイト数（big-endian 32bit） |
| 11 | チェックサム（0..10 の XOR） |

このヘッダにより、**バラバラの順序でページを読み込んでも正しく結合**でき、
ズレた読み取りは**チェックサムNGで検出**して赤枠の再調整を促します。

**モード自動判別**: デコーダはカードのモードを事前に知りません。そこで
1KB・2KB・3KB・4KB すべてのグリッドでヘッダ行を試し読みし、`MAGIC` + `checksum` が通り、
さらに**ヘッダ内モードIDとサンプリングに使ったグリッドが一致**したものを採用します。
これにより、読み取り側でモードを手動選択する必要はありません。

### 自動位置検出
四隅に **黒い正方形のファインダマーカー**を配置しています。左上(TL)だけは
「黒四角の中に白抜き＋中心に黒点」の特別マークにして**向きを一意**にしています。

デコーダは以下の流れで四隅を自動検出します（歪みなし・まっすぐ動かす前提）:

1. グレースケール化 → **大津の二値化**（縮退対策として黒/白平均の中点を採用）
2. **連結成分ラベリング**で黒い塊を抽出
3. サイズ・アスペクト比・充填率で「ファインダらしい塊」を選別
4. 画像の四隅に最も近い塊の重心を採用
5. ファインダ中心 → データグリッド四隅へ幾何補正（`finderToGrid`）

検出できない/ズレる場合は、赤枠の四隅を手で合わせれば確実に読めます。

## 🧪 テスト

Node.js（Canvas不要の純JS）で往復一致を検証します。

```bash
npm test                       # roundtrip + autodetect をまとめて実行
# 個別に実行する場合:
node test/roundtrip.test.js    # 生成→理想座標サンプリング→復元 が byte-exact
node test/autodetect.test.js   # 生成→自動検出(otsu+連結成分)→復元 が byte-exact
```

実Canvas + 実JPEG(0.9)圧縮を経た自動検出E2E（特に **4KBモードの高密度セル(1.06mm)が
JPEG圧縮後も読めること**の確認）は Node でも実行できます（`canvas` が必要）。

```bash
npm install                    # devDependency の canvas を導入
npm run test:jpeg              # node test/jpeg-e2e.node.js
```

ブラウザでの実描画・実JPEG圧縮を含むE2Eは、静的サーバを立てて開きます。

```bash
python3 -m http.server 8000
# → http://localhost:8000/test/browser-e2e.html （タイトルが "E2E PASS" になれば成功）
```

検証済みケース（**1KB / 2KB / 3KB / 4KB 各モード**）: 小さいテキスト / モード容量ぴったり(1KB・2KB=2048B・3KB=3072B・**4KB=4096B**) /
複数ページ / スキャン解像度違い(1.3x) / 余白(平行移動)付き /
**JPEG圧縮(0.9)経由**（特に **4KBモード(1セル 1.06mm)が JPEG圧縮後も読めること**） / **モード自動判別**。いずれも byte-exact で復元。

## 💡 印刷・スキャンのコツ

- 印刷は **等倍（100% / 実サイズ / 拡大縮小なし）** が理想。
- 白黒でOK。**四隅の黒い■を切らない**（自動位置合わせに必須）。
- スキャンは **300dpi 前後**。傾き・歪みは無い前提なので、原稿はまっすぐ置く。
- 撮影する場合は真上から、影・反射が入らないように。
- うまく読めないときは Decoder の赤枠を手動で微調整、または「白黒反転」を試す。
